# 分流规则改为 Clash 式弹窗编辑

日期：2026-11-05
状态：已实现

## 背景

现在的分流规则是面板里一张内嵌表格，列有 类型 / 匹配值 / 走向 / no-resolve / 启用 / 备注 / 操作。对只想"给某个域名指定走 VPN 还是直连"的用户来说，信息过密：no-resolve、备注这些选项既看不懂，也很少改。

改成 Clash Verge 那种方式：面板只做只读预览，增删改序都在一个「编辑规则」弹窗里完成，弹窗左边是四个输入项。

## 目标

1. 规则入口收进动作栏：面板不再放规则卡片，动作栏在「连接」后面加一个「规则」按钮
2. 弹窗：左边四个输入项（规则类型、规则内容、代理策略、备注）+ 右边现有规则列表
3. 规则顺序：只有一个「添加规则」按钮（追加到末尾），每条规则 hover 出 ↑↓ 调整顺序
4. 不再提供兜底 MATCH 走向：没命中任何规则就走直连（和 Clash 的 MATCH 默认直连一致），列表里也没有兜底行
5. 启用/停用保留为行内小开关

## 不在范围

- 实时连接日志 / 拦截日志（另一个需求，稍后单独做）
- REJECT 拦截策略（规则走向仍为 DIRECT / VPN）
- 规则分组、规则集、订阅

## 界面

动作栏（详情右上角）从左到右：

```
[连接] [规则] [检测] [日志] [删除]
```

- `连接` / `断开`：原来的「连接 VPN」缩短；同通道切换时仍显示「切换到该配置」
- `规则`：打开规则编辑弹窗
- `检测`：重新探测连接器（原「重新检测连接器」）
- `日志`：从右侧滑出实时日志抽屉
- `删除`：删除当前配置（保留原有二次确认）

日志抽屉：

- 顶部：标题 + 状态（已连接/连接中/未连接）、`暂停跟随`、`清空`、`打开日志目录`、关闭
- 内容：实时日志流（时间 + 级别 + 文本），默认跟随底部滚动，用户点暂停后停在当前位置
- 空状态：提示连接后会出现隧道建立、DNS、规则命中等过程日志
- 说明：这里展示的是 worker 现有的运行日志流，不是 Clash 那种每条连接一行的判定日志（后者另一个需求）

弹窗（宽 ~760，左表单 300 + 右列表自适应）：

- 规则类型下拉**只保三类**，顺序按「最常用在前」：域名后缀 DOMAIN-SUFFIX / 完整域名 DOMAIN /
  IP 网段 IP-CIDR；**默认选中 DOMAIN-SUFFIX**（Windows 的 NRPT 精确匹配只覆盖裸域名，
  绝大多数场景要的是「这个域连同所有子域」，所以把它放第一个并设为默认）。
  早先还有 DOMAIN-KEYWORD / PROCESS-NAME / DST-PORT，规则模式改成路由注入后这三类
  没有数据面可用、写了也不生效，已从下拉下架（历史配置里若还留着，列表里打「不生效」标记，
  能删不生效）。
- 规则内容输入框：placeholder 固定为「请输入」，不再按类型写示例长句（示例太长、看着像已被填好）
- 表单只有三项：规则类型、规则内容、代理策略。**没有备注、没有启用开关**（启用开关只在右侧
  列表行上；备注字段从表单撤掉，老数据里的 `remark` 原样保留不动）
- 新建配置**不再预置任何规则**。`example.com` 是开发环境数据，不能写进生产包；
  默认规则属于用户配置，必须由用户显式添加。
- 代理策略下拉：直连 DIRECT / 走 VPN
- 「添加规则」按钮：校验 → 追加到末尾 → 清空内容框，焦点回内容框。编辑已有规则时按钮变成
  「保存修改」（旁边多一个「取消」），校验通过后**原地更新**，顺序不变
- 不显示 MATCH 兜底行：没命中就是直连，不需要单独一行；列表为空时只留一句提示文字
- 右侧规则行：序号 + 值 + 类型标签 + 策略 + 操作区（编辑 / ↑ / ↓ / 删除）+ 启用开关。
  行内不再显示「已禁用」标签（开关本身就是状态）也不再显示备注
- 编辑入口：点行上的编辑按钮，或双击整行；编辑按钮用项目分组模块那套铅笔 SVG，删除用
  同一套的叉号 SVG，和主界面图标语言一致
- 底部只留「完成」，表单下方也不留任何提示文字

## 行为

- **关闭才生效**：弹窗里的增删改序、启停都只改本地草稿；点「完成」、点 ×、点遮罩关闭时，只有草稿与原值不同才写一次配置，已连接且是当前生效配置时再热推送一次。只是打开看一眼再关掉不会产生任何写入
- 校验复用后端 `vpn_validate_rule`：它成功时返回归一化后的匹配值（IP-CIDR 会把写法规整，其它类型原样返回），失败时抛错。前端把返回值当作最终规则值，不能把返回值当错误
- 内容为空或格式错误时输入框红框 + 下方红字，不写入
- 完全相同的「类型 + 值 + 策略」拒绝添加，提示"已有相同规则"（前端比较，不往返后端）
- 新规则默认 `enabled: true`、`no_resolve: true`（与引擎默认一致；该字段仅对 IP-CIDR 有意义，UI 不再暴露）
- **编辑一条被禁用的规则并保存 → 这条规则变成启用**：表单里没有启用开关，改内容就是对它
  「重新启用」；只想停用不想改内容，直接点行上的开关
- 老数据里的 `remark` 不再展示，也不再能编辑；保存编辑时原样保留（不主动清空）
- 规则类型下拉：`DOMAIN-SUFFIX`（默认选中）→ `DOMAIN` → `IP-CIDR`，按最常用排序

## 修复：规则重启后丢失

**现象**：在弹窗里加好规则、连接时却提示「这个配置还没有启用的规则」；重启应用后规则列表变空。

**根因**：规则从「全局规则集 + rule_set_id 引用」改成「内嵌在配置里」时，只改了前端模型和迁移脚本，后端持久化的 `VpnProfile` 结构没有 `rules` / `rules_default_policy` 字段。`save_config` 按后端结构序列化整份配置，规则在落盘时被静默丢掉，重启读回来自然就是空的（旧模型的 `rule_set_id` 也一起丢了，所以迁移逻辑再也看不到老数据）。

**改法**：`VpnProfile` 补回 `rules` 与 `rules_default_policy`（带 serde 默认值，兼容老配置），`rule_set_id` 也保留为可选字段，让前端迁移逻辑仍能读到；新增「规则写入配置文件再读回来不能丢」的回归测试。连接时的兜底走向统一为：规则模式没命中→直连，全局模式→VPN，直连模式→直连。

## 诊断：为什么「域名含 corp」没命中

`DOMAIN-KEYWORD` 的语义就是「host 里包含这段子串」（大小写不敏感），`oa.example.com` 含 `corp`，按规则本身必然命中，`rule_engine` 测试 `keyword_rule_matches_anywhere_in_host` 覆盖了这一点。

真正会让人误以为「匹配不到」的是**引擎拿不到域名**：域名类规则只有在引擎看到应用发的 DNS 查询（被 fake-ip 接管）时才有 host 可比。以下情况连接到达引擎时只有真实 IP、没有 host，域名规则一律不参与匹配，直接落到兜底直连：

- 应用/浏览器在连接 VPN 之前就缓存了这条域名的 IP，或用长连接复用；
- 应用自己走 DoH / 私有 DNS，查询没经过系统 DNS；
- 访问时直接填了 IP；
- 域名命中 `fake-ip` 过滤名单（`fake_ip_filter`），引擎按真实地址应答。

为了能一眼看出是哪一种，引擎现在会把诊断写进「日志」抽屉（`worker.log`）：

```
[DNS] oa.example.com -> 198.18.0.7（假地址，连接时会按域名匹配规则）
[分流] oa.example.com:443 -> VPN（命中 DOMAIN-KEYWORD corp）
[分流] 192.0.2.41:443（无域名） -> 直连（兜底，域名类规则不参与匹配）
[分流] 10.0.0.5:443 -> VPN（命中 IP-CIDR 10.0.0.0/8），建连失败：路由不可达
```

`CompiledRuleSet::evaluate_hit` 负责把命中的那条规则一起带出来（`evaluate` 保持原语义不变）。

## 规则模式「一连上就没网」的定位手段

用户反馈规则模式下整机断网，且兜底直连也不通。此前「已接管」之后引擎完全静默，无法区分是捕获网卡没收到包、DNS 没应答、还是直连出口建不起来，所以加了三组诊断：

1. **连接后自检**（`worker.rs::spawn_self_check`，独立线程）：解析 `www.baidu.com` → 判断拿回的是 fake-ip 还是真实地址 → 用这个地址建一条真实 TCP 连接。这一条把「应用 → 捕获网卡 → 引擎 → 直连出口 → 回包」整条链路串起来，日志里直接能看出断在哪一段。
2. **引擎计数**：捕获网卡收/发包数、DNS 伪造应答数、新连接数、建连失败数，每 5 秒变化时写一行。
3. **每条连接的分流结论**：`[分流] 域名:端口 -> 出口（命中规则/兜底）`，失败时附上错误原因。

另外加了兜底：引擎接管后 12 秒内捕获网卡一个包都没收到，就撤掉半默认路由并刷新 DNS 缓存，把网络还给直连——宁可这一趟规则分流不生效，也不能让用户面对「一连上就全网断」。

## 根因：smoltcp 0.11 的 AnyIP 还要求一条默认路由

日志证据：接管后 `收 N 包 / 发 0 包 / DNS 应答 0 / 新连接 0`，系统 DNS 最终解析失败，整机没网。

`Interface::set_any_ip(true)` 只打开了开关，smoltcp 0.11 的接受条件比这严格（`iface/interface/ipv4.rs`）：

```rust
if !self.has_ip_addr(dst) && ... {
    if !self.any_ip                       // 1. 开了 AnyIP
        || !dst.is_unicast()              // 2. 目的是单播
        || self.routes.lookup(&dst, now)  // 3. 路由表里能查到一条前缀
            .map_or(true, |gw| !self.has_ip_addr(gw))  // 且其网关是本接口自己的地址
    {
        return None;   // 静默丢弃
    }
}
```

捕获网卡只配了 `10.9.0.1/32`、路由表是空的，第 3 条永远不成立 → **所有包在进入 socekt 分发前就被丢光**，于是收包计数一直涨、发包恒为 0、DNS 不应答、整机失联（这个版本之前用旧版 smoltcp 时没有这条限制，所以是升级后引入的回归）。

修法：装配 iface 时补一条默认路由，网关指向自己的捕获地址 `10.9.0.1`。回归测试 `packets_for_arbitrary_destinations_are_accepted` 覆盖（去掉这行路由测试立刻失败）。

## 根因二：绑网卡（IP_BOUND_IF）在捕获路由下必然失败

AnyIP 修好后引擎活了（`收 732 包 / 发 498 包 / DNS 应答 16`），但所有出站都失败：

```
[分流] www.baidu.com:443 -> 直连（兜底），建连失败：Network is unreachable (os error 51)
[分流] vpn.example.com:1218 -> 直连（兜底），建连失败：Can't assign requested address (os error 49)
```

原因是出站 socket 用 `IP_BOUND_IF` 钉在物理网卡上。绑定后 socket 的选路只看**绑定网卡自己的路由**，
而捕获网卡已经抢了 `0.0.0.0/1` + `128.0.0.0/1`（覆盖全部 IPv4），于是绑定物理网卡的 connect
找不到可用路由，直接 `ENETUNREACH`/`EADDRNOTAVAIL`。整机所有直连都断，表现就是「百度一直 pending」。

改成按需装 /32 路由，不再绑网卡：

- 直连流：`route add -host <真 IP> <物理网关>`
- VPN 流：`route add -host <真 IP> -interface utun4`（原有逻辑）
- 落在本机直连网段（如 `192.168.1.0/24`）的地址：`-interface en0` 走 on-link，不能经网关绕一圈
- 同 IP 多条流共用一条路由，引用计数归零才删

好处：不依赖各平台 socket 选路实现（`IP_BOUND_IF` / `IP_UNICAST_IF` 的语义差别很大），
行为与其它分流工具一致；代价是每个新目的地址一次 `route` 调用。

顺带把重复的建连失败日志收敛成「第 1/2/10/20… 次」，避免一次断网刷出上百行。

## 根因三：不绑源地址时，捕获路由让内核选不出源地址

改成 /32 路由后连接从 `ENETUNREACH(51)` 变成统一的 `EADDRNOTAVAIL(49)`。
`EADDRNOTAVAIL` 是 `in_pcbladdr`（源地址选择）失败：捕获网卡占着 `0.0.0.0/1` + `128.0.0.0/1`，
未绑定源地址的 socket 让内核自己选源时选不出来。

修法：出站 socket 显式绑定源地址，源地址选择不再经过路由表：

- 直连：绑定物理网卡 IPv4（启动时用 `getifaddrs` 取，日志里会打出来）
- VPN：绑定隧道下发地址 `vpn_ip`
- 路由仍然按流装 /32，负责把包送对网卡

另外失败诊断加了一行 `[诊断] 内核选路 <ip> -> interface/gateway`，
下次「连不上」时能直接看到内核把包送给哪块网卡、走哪个网关。

## 根因四：删了不该删的路由 + 丢字节把 TLS 写坏

这一轮日志的关键证据：

```
[分流] vpn.example.com:1218 -> VPN（命中 DOMAIN-KEYWORD corp），建连失败：No route to host (os error 65)
[诊断] 内核选路 203.0.113.10 -> gateway: 192.168.1.1；interface: en0
...
[诊断] 内核选路 203.0.113.10 -> destination: default；interface: utun5
```

两个独立问题：

### 1. 引擎把 vpnc 脚本装的「VPN 服务器防环主机路由」删掉了

`203.0.113.10` 已经有一条 `via 192.168.1.1` 的主机路由（脚本加的，防止隧道自己的包绕回隧道）。
引擎给 VPN 出口装 /32 时拿到 `File exists`，当成"已存在"继续；但**流结束时照样删了它**。
结果隧道自己的报文开始走捕获网卡 → 死循环，隧道断、`corp` 站点直接网络不通。

修法：
- 装路由时区分「我们新建的」和「已经存在的」，只有前者才在流结束时删除
- 已经存在的路由，出站 socket **不绑本出口源地址**（硬绑隧道 IP 但路由走 en0 会 `No route to host`）
- VPN 服务器自身 IP 完全交给 vpnc 脚本，引擎不碰（`server_ips`）

### 2. 代理侧丢字节 → TLS 坏 → Chrome 提示「此网站不支持安全连接」

`pump_tcp` 以前是：

```rust
let _ = router.egress_write(&key, &buf[..n]);   // 忽略返回值
```

出站 socket 带 200ms 写超时，非阻塞下经常只写进一部分甚至只能写 0 字节：
- 写进一部分 → 剩余字节被丢掉
- `TimedOut` → 整块 16KB 丢掉

被丢的字节直接进垃圾堆，TLS 记录被截断，浏览器就报「此网站不支持安全连接」/「连接已重置」，
或者跳到奇怪的页面。同理「出站 → 应用」方向在应用窗口满时也会丢。

修法：两个方向都加缓冲 + 反压
- 应用 → 出站：先收进 `pending_in`（上限 1MB），每轮尽量写；到上限就不再从应用侧 socket 读，让 TCP 窗口自己反压
- 出站 → 应用：应用窗口不够时把没发完的字节退回 `pending_out`，下一轮按原顺序补发

### 诊断增强

- 建连失败的错误信息里直接带「预期出口/源地址 + 内核实际选路」，且是在释放路由**之前**读的
- 统计行多了「连接尝试」：`收 / 发 / DNS 应答 / 连接尝试 / 新连接 / 出站异常`。
  内网域名如果连尝试都没有，说明 SYN 没进引擎；有尝试没新连接，说明解析或出口有问题。

## 根因五：引擎循环被读写超时卡住

出站 socket 之前带 200ms 读写超时。引擎是单线程轮询，`read` 没数据时**阻塞 200ms**，
N 条流就是 N×200ms：6 条流一轮就要 1.2 秒，TLS 握手要几个来回，网页自然一直 pending。

修法：建连完成后统一 `set_nonblocking(true)`，读写拿 `WouldBlock` 当"这轮没有"，
攒下来的数据进缓冲、下一轮继续。`dns_exchange` 也改成非阻塞 + 2ms 让出 CPU 的轮询。

## 回归测试：双向 512KB 不能丢、不能乱序

`router` 里用真实 loopback socket 对打：

- `buffered_uplink_never_loses_bytes`：灌 512KB 进上行，期望对端一个字节不少收到
- `buffered_downlink_never_loses_bytes`：对端写 512KB，期望按原顺序收全
- `restored_downlink_keeps_byte_order`：应用窗口满时退回缓冲的字节顺序不变

写这些测试时还抓到一个真实 bug：窗口满退回的字节用 `push_front` 是错的（会插到积压数据
前面并整体倒序），必须 `push_back`。

## 统计行

```
[引擎] 收 N 包 / 发 M 包 / DNS 应答 K / 连接尝试 A / 新连接 S / 出站异常 F / 上行 X KB / 回程 Y KB
```

判读：
- `上行 > 0，回程 = 0`：出站连上但对方不回（多半是 IP 被墙/服务端没响应），跟代理无关
- `回程 > 0` 但页面还是 pending：问题在应用侧投递，继续查
- `连接尝试` 不涨：SYN 根本没进引擎

## 根因六：域名解析是同步的，一次最多卡 3.5 秒，失败还不缓存

fake-ip 流到达时要先把域名解析成真实 IP，`resolve_name` 以前的重试阶梯是

```
应用 DNS 1200ms -> 换出口 800ms -> VPN DNS 700ms x N -> 公共 DNS 800ms
```

全部失败要 3.5 秒以上，而这期间**单线程引擎完全停摆**（所有流一起卡），
而且失败结果不缓存，页面上每次重连都要再卡一遍 —— 表现就是"所有网站一直 pending"。

修法：
- 每步超时收紧到 400 / 250 / 250×N / 300 ms
- 加 60 秒**负缓存**：解析失败的域名直接快速失败，不再反复卡引擎


## 根因七：「一连上就全网断」是系统解析器被半默认路由打断

现场日志（worker.log，引擎刚接管之后立刻开始）：

```
[引擎] 已接管：捕获 utun5 (10.9.0.1) -> 隧道 utun4
[自检] 系统 DNS 解析失败：failed to lookup address information: nodename nor servname provided
```

同时 `mDNSResponder` 的系统日志里是：

```
[DNS] mDNSResponder: Sent 41-byte query #1 to <IPv4:192.0.2.12> over UDP via en0/14
[DNS] mDNSResponder: sending to <IPv4:192.0.2.12> failed: [51: Network is unreachable]
```

**系统解析器根本发不出 DNS 查询**。原因：macOS 给每个网络服务建的是「接口限定」的
resolver，mDNSResponder 的查询 socket 钉在物理网卡（`IP_BOUND_IF(en0)`），
选路时只认 `en0` 自己的路由。捕获 TUN 抢走 `0.0.0.0/1` + `128.0.0.0/1` 之后，
`en0` 上已经没有去 DNS 服务器的路由了，`sendto` 直接 `ENETUNREACH(51)`。

后果：所有走系统解析器的 App（Safari、App Store、绝大多数原生应用、命令行、自检）
一个域名都解析不出来。公网其实没断，但「DNS 全挂」对用户来说就是断网。

修法（安全优先，遵循「宁可这一趟规则不生效，也不能让用户面对断网」）：

1. 把**系统 DNS 服务器**和 VPN 服务器一样，用 /32 主机路由钉在物理网关上
   （`route::system_dns_servers()` 从 `scutil --dns` 读，去重、跳过回环/IPv6）。
   系统解析器立刻恢复可用，代价是这类解析不走 fake-ip：系统解析器拿真实地址，
   这类应用的连接按「无域名」走兜底策略。自带解析器的应用（Chrome/Electron/curl）
   的查询照样被捕获网卡接住，fake-ip 与域名规则照常生效。
2. 这些旁路地址同时交给引擎的「不要碰」名单（和 VPN 服务器同一份），
   引擎既不装也不删它们的路由 —— 否则引擎查一次 DNS 就会把旁路路由删掉，DNS 又挂。

> **注意：这一版的修法已被真机复测推翻。** 加了 /32 直连旁路之后，
> `mDNSResponder` 的报错从 `[51]` 变成 `[49]`，系统解析器照样解析不出域名。
> 详见下面的「根因九」，最终落地的是安全阀（探不通就放弃接管），
> 而不是继续加路由。

## 根因八：路由「已存在」被吞掉，引擎把别人的路由当成自己的

`route -n add` 在 macOS 上遇到 `File exists` 会被 `run_route_macos` 当成成功，
于是 `retain_flow_route` 认为这条 /32 是自己新建的，返回「按出口绑源地址」；
但内核实际用的是**现成的那条路由**（例如 vpnc 脚本给 VPN 服务器加的防环主机路由，
走 en0），源地址绑成隧道地址后 `connect` 直接 `EADDRNOTAVAIL`：

```
[分流] vpn.example.com:1218 -> VPN（命中 DOMAIN-KEYWORD corp），
       建连失败：Can't assign requested address (os error 49)
       （预期VPN if#22 源 198.51.100.39；内核选路 gateway: 192.168.1.1 interface: en0）
```

更糟的是流结束时 `release_flow_route(created=true)` 会把这条**别人的**路由删掉，
VPN 服务器的防环路由一没，隧道自己的报文就绕回捕获网卡，隧道随即断。

修法：

- macOS 的 `add_route` 不再容忍 `File exists`，让调用方看见「路由已存在」，
  从而走「不绑源地址、不删路由」的分支
- 捕获路由先按前缀清残留再加（`remove_route_prefix`），避免上一轮 SIGKILL 留下的
  旧半默认路由把新的捕获变成静默失效
- 服务器/系统 DNS 的防环路由先删再加，残留路由不会让关键路由加不上

## 根因九：路由接管和 macOS 系统解析器不能共存 —— 加旁路是死路

根因七 第一次的修法是「把系统 DNS 服务器也按 /32 钉在物理网关上」。真机复测
（2026-11-05 17:04）结果：

```
17:04:16.340 [路由] 系统 DNS 192.0.2.12 走直连旁路
17:04:16.840 mDNSResponder … sending to <…> failed: [49: Can't assign requested address]
17:04:26.9xx [DNS] settings-bd.feishu.cn -> 198.18.0.1
17:04:47.xxx [自检] 系统 DNS 解析失败（后面几步跳过）
```

关键信息是**错误号从 51 变成了 49**：

- `[51: ENETUNREACH]` = 解析器的查询**没有路由**（半默认路由把表抢走了）；
- `[49: EADDRNOTAVAIL]` = 路由有了，但**源地址分配不出来**。

也就是说 mDNSResponder 的送包姿势是「接口限定 + 源地址指定」，它要么找不到
接口内的路由，要么找不到能用的源地址。再加任何 /32 路由都只是把 51 换成 49，
解析照样失败 —— 系统解析器一废，所有走它的 App 集体「断网」。
同一时间引擎自己的直连建连也偶发同样的 `os error 49`，说明这不是 DNS 独有，
而是「半默认路由 + 绑源地址」这一套和 XNU 的选路/源地址校验在互相打架。

结论：**「抢默认路由做全量捕获」和「macOS 系统解析器」在这台机器上不能共存，
靠路由规则去调停是走不通的。** 继续在这条路上打补丁，只会让用户一次一次
面对「一连上就全网断」。

落地做法（安全阀，已实现）：

1. 抢半默认路由**之前**先量基线（能不能用系统解析器解析一个随机域名）；
2. 抢完再真实解析两次（各 2.5s），两次都没有结果就判定「接管打断了系统解析器」；
3. 立刻把捕获路由还回去（`del_capture_routes`），**不装配引擎**，
   状态显示「已连接（未接管系统流量：…）」，隧道保留、系统流量照常直连；
4. 基线本来就失败的机器（没网/没 DNS）不参与判定，避免离线环境误判。

关键点：宁可这一趟规则分流不生效，也不能让用户面对「一连上就全网断」。
探针用随机域名（`probe<nanos>.example.com`）而不是常见域名，是为了绕开缓存 ——
接管后缓存里的旧答案照样能秒回，用它会骗过探针。

## 下一步：换掉「抢默认路由」这个地基

既然捕获式接管和 macOS 解析器不兼容，规则模式要真正可用，只有两条路：

- **方案 A：本机 DNS 服务 + 接管系统 DNS**（Clash/sing-box 的做法）。
  worker 起一个 127.0.0.1:53 的 DNS 服务，`networksetup` 把系统 DNS 指向它，
  解析请求不再需要「经物理网卡去问远端 DNS」，于是半默认路由怎么抢都不影响解析；
  同时它可以继续返回 fake-ip，域名规则完整保留。代价：要管好 DNS 的改回
  （异常退出、崩溃、断电都要能还原），实现量最大。
- **方案 B：路由注入式分流，完全不捕获**。默认路由和系统 DNS 都不动，
  对命中「走 VPN」的域名：经隧道把域名解析成真实 IP，再给这些 IP 装 /32
  走 utun4；内网域名用 `/etc/resolver/<域>` 指向 VPN DNS。代价：失去进程规则、
  失去「按不可见域名分流」的能力，但**结构上不可能再出现「一连上就断网」**。

方案选择需要产品决策（见对话），安全阀的作用是不管选哪条，先把「断网」按住。

**已选方案 B（用户拍板），落地见下一节。**

## 方案 B 落地：路由注入式分流（规则模式，macOS）

代码：`src-tauri/src/vpn/split.rs`，由 `worker.rs::start_split_rules()` 在连接时拉起。
规则模式下**不再创建捕获 TUN、不抢 `0.0.0.0/1`+`128.0.0.0/1`、不改系统 DNS**。

做法：

1. `split::plan()` 把「走 VPN」的规则翻译成可执行的动作：
   `DOMAIN`/`DOMAIN-SUFFIX` → 域名清单，`IP-CIDR` → 网段清单；
   `DOMAIN-KEYWORD`/`PROCESS-NAME`/`DST-PORT`/`RULE-SET` → 逐条给出「这个模式做不到，
   请改成 DOMAIN-SUFFIX」的提示（没有数据面，确实做不到）。
2. 给 VPN 下发的 DNS（`223.5.5.5`）和 `IP-CIDR` 网段装 `/32`、`/n` 主机路由，**指向隧道**。
3. 给每个域名写 `/etc/resolver/<域名>`，内容是 `nameserver 127.0.0.1` ——
   macOS 官方的「按域名分流解析」机制，系统解析器会把这些域名的查询送到本机。
4. worker 里起 DNS 转发器（`127.0.0.1:53`）：收到查询 → 经隧道转发给 VPN DNS →
   拿到真实内网 IP 时给这些 IP 装 `/32` 隧道路由 → 原样回包。

另外，脚本会把服务端下发的 `CISCO_SPLIT_INC*`（split-include 网段）和
`CISCO_DEF_DOMAIN`（默认域名）回报给 worker，worker 把它们**并进同一份计划**：

- 网段 → 直接注入隧道（正规 VPN 客户端的做法），落这些网段的流量全部走 VPN，
  不管域名是怎么解析出来的（应用自带 DNS、硬编码 IP 都兜得住）；
- 默认域名 → 自动写一条 `/etc/resolver`，整族子域自动走 VPN，用户不用逐个列举；
- 服务端若下发 `0.0.0.0/0`（全隧道），路由注入模式会明确拒绝并提示改用全局模式 ——
  否则 DNS 仍走原来的服务器、流量却全进隧道，等于自造一次「断网」。

这是「把公司相关请求全覆盖」最权威的依据，比用户手写规则准；规则只用来补
服务端没下发的那部分。
5. 收尾：断开时回收 resolver 文件、隧道路由、转发线程并刷新 DNS 缓存；
   进程被 SIGKILL 时靠 `<会话目录>/resolver-manifest.txt` 在下次连接前清理干净。

为什么这条路上不可能再「断网」：默认路由、系统 DNS、其它流量一个都没动，
最坏情况是「分流不生效」（规则没翻译出可用动作、53 端口被占用、resolver 文件写不进去），
此时 worker 只建隧道、不接管任何流量，并在状态里写明原因。

启动 / 变更 / 断开：

- 连接：`start_engine()` 在 macOS 规则模式下直接转 `start_split_rules()`；
- 规则改动：`poll_rules_change()` 检测到规则变化后 `restart_split()` 重新布线（不用重连）；
- 模式切换：分流期间拒绝运行期切模式（要重布线），提示断开重连；
- 断开：`cleanup_routes()` 先 teardown 分流，再走原有回收。

日志关键字（排障按这个顺序看）：

```
[分流] 路由注入模式：域名 [...]，网段 [...]，VPN DNS [...]，隧道 utun4
[分流] 路由注入分流已生效：1 个域名走隧道 utun4，1 条固定隧道路由；默认路由与系统 DNS 均未改动
[分流] 内网 IP 10.10.3.17 已注入隧道 utun4
[自检] 开始：系统解析器 -> /etc/resolver -> 本机转发器 -> 隧道 -> VPN DNS
[自检] example.com 解析到 …（已按隧道路由接管，连接会走 VPN）
```

已知限制（都要让用户知道）：

- `DOMAIN-KEYWORD` 不能直接用于路由注入（没有数据面做关键字匹配），要么改成
  `DOMAIN-SUFFIX`（例如 `corp` → `DOMAIN-SUFFIX example.com`），要么继续用捕获模式；
- 自带 DoH/DoT 的应用不经过系统解析器，域名规则管不到它；如果它解析出的 IP
  命中 `IP-CIDR` 规则，仍能进隧道；
- 兜底策略是 VPN（全隧道）不适用于本模式，需要「全部走 VPN」请用全局模式；
- ~~全局模式暂时仍走捕获引擎~~ 已补齐，见下一节。

## 全局模式 / 直连模式 / 运行期切换（macOS）

规则模式走完以后，另外两个模式退化成同一个问题：**要不要把这台机器的流量交给隧道**。

- **直连**：隧道建起来，一条路由都不加、DNS 不动（`start_engine` 直接返回）。
- **全局**：等价于「在终端里裸跑 openconnect」，照抄系统标准脚本
  `/opt/homebrew/etc/vpnc/vpnc-script` 在 Darwin 上的动作（`src-tauri/src/vpn/fulltunnel.rs`）：
  - 路由：`0.0.0.0/1` + `128.0.0.0/1` 指向隧道。**故意不删**系统原有 default ——
    删掉这两条半默认路由就完整恢复，比标准脚本「备份 default → 重装 → 断开装回」
    少一次破坏性操作；本地网段是连接路由，天然比 `/1` 更具体，自动保持直连。
  - DNS（较新 macOS 上标准脚本也是两处都写，实测终端 openconnect 能上网靠的就是它）：
    `scutil` 给隧道服务写 `State:/Network/Service/<tun>/IPv4` 与 `.../DNS`
    （带 `OverridePrimary # 1`，让系统优先用这份 DNS）；
    `networksetup -setdnsservers <当前活动网络服务> <VPN DNS>`。
  - 还原：断开时隧道服务整段移除，活动网络服务恢复连接前的快照
    （快照为空 = 原来走 DHCP，设回 `Empty`）。
  - 崩溃兜底：改 DNS **之前**先写 `fulltunnel.marker`（服务名 + 原 DNS），
    worker 启动时 `restore_stale()` 先还原。否则被 SIGKILL 后残留的 `223.5.5.5`
    会被当成「用户自己配的 DNS」快照下来，从此再也回不到 DHCP。
  - 安全阀：装完立刻 `verify_system_resolution`，连续两次失败就整段回滚
    （路由与 DNS 都还原）并降级 —— 绝不留「DNS 死了、路由还在」的黑洞。
- **运行期切换**：三种模式本质都是「布几条路由 + 改不改 DNS」，所以
  `switch_mode()` 直接撤旧布线、布新线，不必断开重连；`status.applied_mode`
  记录本次会话实际生效的模式，界面按它高亮（此前的 bug：界面显示「全局」，
  worker 里其实还是规则模式，内网能通纯属规则分流在干活）。

对比一句话：规则模式结构上不可能断网（默认路由与系统 DNS 都不动）；
全局模式一定会动系统 DNS，这是全隧道的本质，只能靠快照 + 验证 + 回滚兜住。

- 删除正在编辑的规则会自动退出编辑态；历史类型（`DOMAIN-KEYWORD` 等）没有对应的下拉项，
  ✎ 置灰，提示删掉重建；
- 新增「备注」输入（可选，40 字上限），新增与编辑时都能填。

### 启用 / 禁用

- 新增规则**默认启用**（`enabled: true`）；禁用的规则仍然保存在配置里，只是不参与分流匹配
  （后端 `split::plan()` 会跳过 `enabled == false` 的规则）。
- 左侧表单加「启用状态」开关，新增和编辑时都能直接设；编辑已有规则会回填它当前的状态，
  保存后立即反映到列表。
- 右侧列表每行保留开关（hover 显示），并在行内打「已禁用」标记 + 值加删除线；
  列表头显示「N 条 · M 条启用」，一眼能看出有几条没生效。

顺带一提：这也让「把 `DOMAIN-SUFFIX example.com` 改成 `IP-CIDR 192.0.2.0/24`」这种
调整不需要删规则重加了。
